The folder listing exposes per-item file name, extension, item type, size, created/modified timestamps, a Graph `driveItem.id`, parent reference, and web/display URL fields. Exact item metadata also exposes the library's `drive_id`, SharePoint `list_id`, numeric `list_item_id`, GUID `list_item_unique_id`, site/web IDs, an eTag, and QuickXorHash. Microsoft Graph documents `driveItem.id` as unique within a drive and persistent when an item is renamed or moved within that drive; a path changes with a rename or move. For a Graph-based connector to this single library, the recommended source key is the configured `source_connection_id` for the drive plus `driveItem.id`. SharePoint `list_item_id` identifies a row within its list; `list_item_unique_id` is a GUID for an item within SharePoint/OneDrive for Business. `eTag` is a version/concurrency value for metadata and content, while `QuickXorHash` can indicate content changes; neither is the item key. Graph's move operation cannot move items between drives, and copying creates a new drive item, so do not assume the same key across libraries or copies. IT and the SharePoint owner still need to approve the future Graph connector route and its source scope. See [Microsoft Graph driveItem addressing](https://learn.microsoft.com/en-us/graph/onedrive-addressing-driveitems), [driveItem](https://learn.microsoft.com/en-us/graph/api/resources/driveitem?view=graph-rest-1.0), [SharePointIds](https://learn.microsoft.com/en-us/graph/api/resources/sharepointids?view=graph-rest-1.0), [move](https://learn.microsoft.com/en-us/graph/api/driveitem-move?view=graph-rest-1.0), and [copy](https://learn.microsoft.com/en-us/graph/api/driveitem-copy?view=graph-rest-1.0).

Microsoft Graph defines `driveItem.createdDateTime` as the service's item-creation timestamp. Its separate `fileSystemInfo.createdDateTime` can reflect the local file's original creation time and may differ; `fileSystemInfo` was not present in the sampled metadata. See [driveItem](https://learn.microsoft.com/en-us/graph/api/resources/driveitem?view=graph-rest-1.0) and [fileSystemInfo](https://learn.microsoft.com/en-us/graph/api/resources/filesysteminfo?view=graph-rest-1.0).

Two representative list rows (one per year) exposed `Title` (populated in both samples), `Date` (populated in one sample), `ContentType`, `Created` (populated in both), `Modified`, `FileLeafRef`, `FileSizeDisplay`, `AuthorLookupId`, `EditorLookupId`, and `MediaServiceImageTags`, plus standard SharePoint version and compliance fields. The sample schema did not expose topic, presenter, duration, language, or transcript fields. `AuthorLookupId` and `EditorLookupId` are person-lookup fields; their values were not reviewed or copied. These population counts are from two sample rows, not all 28 files.

The Product Owner requires `Title` on every resource and approved the source file name as the fallback when `Title` is empty. The bounded retry found an empty `Title` in one of six exact rows; coverage across all 28 remains unknown because later reads failed. Harun confirmed on 2026-11-20 that per-record fallback is sufficient, so exhaustive coverage is not a blocker for ticket 5.4. Apply existing SharePoint ACLs and any visible label to fallback names; no extra classification is required when no folder label is visible.

A bounded retry evaluated only the presence of `Title`, `Date`, and `Created` on six exact list rows; at least one had an empty `Title`, and `Date` varied across the rows. `Created` was populated on these six. Further exact reads returned connector errors, so coverage across all 28 remains unknown. No field values or filenames were copied.

The Product Owner approved the date semantics above. The catalog dictionary in ticket 5.3 still needs to encode separate session-date and source-added-date meanings without treating `Created` as an event date.
